# Add schema combinators and object/collection composition

Difficulty: High

## Background

After the result/issue model in 020, the next gap against Zod is schema composition.
The current YAVI APIs are:

- `am.ik.yavi.core.ValueValidator<T, X>` with `map`, `andThen`, `compose`, `indexed`,
  `liftCollection`, `liftList`, `liftSet` and `liftOptional`. There is no `optional`,
  `default`, `nullable`, `or` or `refine`.
- `am.ik.yavi.validator.Yavi.arguments()` returns `am.ik.yavi.builder.YaviArguments`,
  whose `_string` / `_integer` / `_object` methods add one scalar positional argument
  and whose terminal is `ArgumentsNValidatorBuilder.apply(FunctionN)`. It cannot:
  - nest a multi-field object as one field with a prefixed path,
  - validate collection or map elements,
  - make a field optional or give it a default,
  - express a cross-field rule (password confirmation, date ranges),
  - express a union of alternatives.
- `am.ik.yavi.builder.ValidatorBuilder` already has `nest(Function, String, Validator)`
  with the `NestedValidator` prefix mechanism, and `ValueValidator.liftList` /
  `liftCollection` / `liftTraverse` handle element validation with indexes. Reuse these
  instead of inventing a parallel mechanism.
- `am.ik.yavi.builder.ArgumentsNValidatorBuilder` is generated by
  `scripts/generate-args.sh`; any new field kind or metadata must be added to the
  generator so all arities stay consistent.

## Proposed API

The exact entry point is open; the shape below is the target. It may be a new
`Yavi.schema(...)` entry or an extension of `Yavi.arguments()`.

```java
Schema<Map<String, Object>, User> userSchema = Yavi.schema(User::new)
    ._string("email", c -> c.notBlank().email())
    ._integer("age", c -> c.notNull().min(0))
    ._object("address", addressSchema)          // path: address.street
    ._list("roles", S.enumOf(Role.class))       // path: roles[0]
    ._optional("nickname", S.string())
    .refine((candidate, ctx) -> ...);           // cross-field rule
```

Combinators on the value-schema API:

```java
ValueValidator<String, Optional<String>> optionalNickname = S.string().optional();
ValueValidator<Integer, Integer> ageOrDefault = S.integer().defaultValue(0);
ValueValidator<Object, Shape> shape = S.or(circleSchema, squareSchema);
```

## Scope

- Add `optional`, `default`, `nullable`, `or` and `refine` with clear semantics for
  null, absent and defaulted values.
- Add `_object(name, schema)`, `_list` and `_map` field kinds with prefixed/indexed
  paths.
- Add a terminal cross-field refinement to the arguments/schema builder.
- Update `scripts/generate-args.sh` so the generated builders carry field metadata
  (name, kind, optionality) across all arities.
- Report composition failures through the structured path from 020.
- Add tests for nested objects, indexed collections, optional/default fields, unions
  and cross-field refinement.

## Design questions to settle

- Whether to add a new `Yavi.schema(...)` entry or extend `Yavi.arguments()`. A separate
  entry risks duplicating the generated builders; extending the existing one risks
  breaking its source compatibility. Prefer extending it with a new terminal type if a
  source-compatible path exists.
- Semantics of `optional`: absent key vs `null` value vs `Optional<T>`. In Java, a
  positional constructor cannot omit an argument, so an "optional field" is mostly
  meaningful for 022's `Map` input and for `null` handling.
- Semantics of `or`: how to aggregate the failures of all branches (Zod reports a
  union-level issue with nested issues) and how to keep messages readable.
- Default values: whether a default applies to a missing key only or also to `null`.
- Naming: `_optional` / `_default` versus combinators on the value schema.
