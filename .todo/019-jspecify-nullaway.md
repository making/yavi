# Replace JSR 305 with JSpecify and NullAway

Difficulty: High

## Background

YAVI ships its own copy of the JSR 305 annotations (`am.ik.yavi.jsr305`) and an optional
`com.google.code.findbugs:jsr305` dependency. JSR 305 is dormant and its nullness
semantics are not understood by current tools. JSpecify is the successor, and NullAway
can enforce the annotations at build time. The user has approved this migration.

Use `am.ik.maven:nullability-maven-plugin` for the NullAway setup, following the
java-code-standards skill, instead of wiring Error Prone by hand.

This follows 018 because NullAway and Error Prone need a modern JDK. It must be done
before 020-022 so the new sealed types and records are written against the final
nullness model.

## Current state

- `src/main/java/am/ik/yavi/jsr305` contains `NonNull`, `NonNullApi`, `Nullable` and
  `package-info.java`.
- There are about 144 imports of `am.ik.yavi.jsr305` across main and test sources.
- `pom.xml` declares `com.google.code.findbugs:jsr305:3.0.2` as optional, and the
  license plugin excludes `src/main/java/am/ik/yavi/jsr305/*.java`.
- `@NonNullApi`, `@NonNull` and `@Nullable` are part of the public API surface.

## Scope

- Delete the vendored `am.ik.yavi.jsr305` package and replace the imports with
  `org.jspecify.annotations.Nullable`; package-level `@NullMarked` is generated by the
  Nullability plugin.
- Add `org.jspecify:jspecify:1.0.1` as a compile-only dependency; the annotations must
  not become a runtime dependency. Remove the JSR 305 dependency and the license-plugin
  exclusion.
- Add `am.ik.maven:nullability-maven-plugin:0.5.1` with `<extensions>true</extensions>`,
  the `configure` and `generate-package-info` goals, and `<checking>tests</checking>`,
  following the java-code-standards skill. Fail the build on NullAway findings.
- Do not eagerly annotate parameters and return values with `@Nullable`. Keep the
  default non-null model and fix the findings that `mvn compile` reports by making the
  code null-safe; add `@Nullable` only where null is genuinely required.
- Enable JSpecify-aware nullness in the Kotlin compilation
  (`-Xjspecify-annotations=strict`) and make sure the Kotlin extensions still compile.
- Update the Javadoc that mentions the removed annotations.

## Implementation notes

- The plugin is the source of truth for the Error Prone/NullAway configuration. Do not
  duplicate its compiler flags by hand; if the project needs extra options, expose them
  through the plugin configuration.
- The build currently passes `-proc:none` to `maven-compiler-plugin`; make sure the
  plugin's annotation processing still runs and that it does not interfere with the
  existing annotation processor tests.
- NullAway may report many existing findings. Fix them rather than suppressing them
  globally; per-package or per-line suppressions need a comment explaining why.
- Check the generated sources and the annotation processor tests are not broken by the
  NullAway setup.

## Acceptance

- No reference to `am.ik.yavi.jsr305` remains.
- A deliberate nullness violation fails the build.
- `./mvnw clean test` and `./mvnw javadoc:jar` pass.
- The published runtime dependency set is unchanged.
