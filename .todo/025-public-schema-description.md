# Expose the schema of a validator as a public description

Difficulty: High

## Background

021 added object, list and map arguments, optional arguments and `anyOf`, but what a
validator expects is not visible from outside. The goal is a public, read-only
description of a validator's input that tools can walk, with JSON Schema output as the
first consumer (OpenAPI, form generation and documentation are others).

021 keeps the per-argument metadata in the package-private record
`am.ik.yavi.builder.ArgumentDefinition` (`name`, `kind`, `type`, `optional`,
`validator`). Making that record public as is would not be enough:

- It lives on the builder and is dropped by `apply(...)`, so a built validator cannot be
  described and a nested `_object(name, validator)` has no fields to show.
- `type` is `Object.class` for `_object` / `_enum` and only the container for `_list` /
  `_map`; the element type is unknown.
- It has no constraints (`minLength`, `maximum`, `pattern`, ...) and no `anyOf`
  alternatives.

So the description has to travel with the validators, not with the builder.

## Proposed shape

Names are placeholders; use YAVI's vocabulary (see "Vocabulary" in the history of 021).

A sealed description tree, for example in `am.ik.yavi.core`:

```java
public sealed interface ValueDescription {
    record Value(Class<?> type, List<ConstraintDescription> constraints) implements ValueDescription {}
    record Object(List<Property> properties) implements ValueDescription {}   // ordered
    record Elements(ValueDescription element) implements ValueDescription {}  // list
    record Entries(ValueDescription value) implements ValueDescription {}     // map
    record AnyOf(List<ValueDescription> alternatives) implements ValueDescription {}
    record Unknown() implements ValueDescription {}
    record Property(String name, ValueDescription value, boolean optional, @Nullable Object defaultValue) {}
}
```

- `ValueValidator` gets a way to return its description (`Unknown` by default, so a lambda
  stays valid). `optional()`, `nullable()`, `defaultValue()`, `prefixed()`, `liftList()`,
  `liftMap()`, `anyOf()`, `map()`, `andThen()` and `constraintOnTarget()` propagate it;
  `compose()` changes the input and yields `Unknown` unless a description is supplied.
- The typed validators (`StringValidator`, `IntegerValidator`, ...) describe themselves as
  `Value` with their type and constraints. The constraints are already reachable:
  `Validator.forEachPredicates` gives each `ConstraintPredicate` with `messageKey()` and
  `args()` (for example `container.lessThanOrEqual` with `[14]`).
- The validator returned by `ArgumentsNValidatorBuilder.apply(...)` describes itself as
  `Object` with one `Property` per argument. `ArgumentDefinition` then either becomes the
  public `Property` or is derived from it; do not keep two parallel models.
- A JSON Schema writer is a consumer of the tree. Keep it dependency-free (emit a
  `Map<String, Object>` tree or a string); decide whether it belongs in this artifact.

## Scope

- Add the public description types and the accessor on `ValueValidator` and on every
  `ArgumentsNValidator` (generated by `scripts/generate-args.sh`).
- Carry the description through the combinators and the builders of 021.
- Map the built-in message keys and arguments to a constraint description that a consumer
  can translate without parsing messages.
- Add a JSON Schema output for objects, lists, maps, optional/default properties, `anyOf`
  and the common constraints (`notNull`, size, range, pattern, email, `oneOf`).
- Test the description of a composed validator and its JSON Schema output.

## Design questions to settle

- Where the accessor lives. `ValueValidator` and `ArgumentsNValidator` are functional
  interfaces whose `map` / `andThen` / `compose` return anonymous classes; each of them
  must forward or reset the description.
- How conditional constraints (`constraintOnCondition`, groups) and cross-field rules
  (`constraintOnTarget`) appear: they have no JSON Schema equivalent in general.
- Whether `required` in JSON Schema follows `optional` only or also `notNull()`. In YAVI a
  value without `notNull()` accepts `null`.
- Whether a type that the builder method does not determine (`_object`, `_enum`, the
  result of `compose`) needs an explicit type token.
- New classes must not introduce a dependency cycle between packages: `core` depends only
  on `fn` and `message`.
